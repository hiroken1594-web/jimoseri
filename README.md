# AI地域商社（ビヨパ）

関西の地産地消をAIでつなぐ、飲食店と地域の生産者のための仕入れ支援 Web アプリです。
地域に少量ずつある農産物の供給を、飲食店が実際に使える **1つの仕入れ案** にまとめます。

- Web アプリ：https://jimoseri.vercel.app
- チーム：beyond the past（大学のチーム開発課題、Issue E「関西の地産地消をAIで繋ぐ」）

> 本アプリは学習・発表用の MVP です。注文の確定・決済・配送は、アプリの外で当事者どうしが行う前提です。

---

## 1. 解決する課題

- 地域の生産者は、1品目あたりの出荷量が少なく、飲食店がまとめて仕入れるには何軒も探して調整する必要がある。
- 飲食店は「明後日までにトマト10kg、形が悪くてもよい」のような条件で探したいが、少量の供給情報は散らばっていて比べにくい。
- そこで、飲食店が書いた文章を AI が条件に整理し、複数の生産者の出品を組み合わせて、**誰から・何kg・いくらで・どこで受け取るか** を1画面の案として示します。

## 2. 主な機能

| 利用者 | 機能 |
|---|---|
| 飲食店 | 自然文での条件入力（AI が品目・数量・日付などを整理し、本人が確認・修正）／複数の生産者を組み合わせた仕入れ案／地図・一覧・スワイプでの出品検索／気になる（お気に入り） |
| 生産者 | 出品の登録・編集（数量・価格・規格外・受渡期間・曜日・時間帯・配送の可否）／受渡拠点の登録／飲食店への取引の提案 |
| 共通 | マッチング（依頼・承認）、取引チャット、取引条件の提案と合意、双方の完了確認、相互レビュー、アプリ内通知、通報 |
| 運営者 | 生産者・受渡拠点の審査（審査待ちの一覧、承認・理由つきの却下、審査の記録）、通報への対応（出品の公開停止など） |
| お試し | デモモード：架空のデモデータ（大阪府内のトマトの出品）だけで、検索から取引の流れまでを試せる |

## 3. 使用技術

- フロントエンド：React 19、TypeScript、Vite、React Router、Leaflet（地図。国土地理院タイル）
- バックエンド：Vercel Functions（Node.js、TypeScript）。API は1つの関数に集約し、URL で振り分け
- データベース：PostgreSQL（本番は Neon、ローカルは Docker）、Prisma ORM
- 認証：Better Auth（ユーザー名＋パスワード、リカバリーコード。メールは使わない）
- AI：OpenAI API（自然文から仕入れ条件を取り出す。サーバー側だけで呼び出す）
- 入力の検証：zod（画面と API で同じルールを共有）
- テスト：Vitest（単体テスト）、Node.js のスクリプトによる API／E2E テスト、Playwright による画面の確認

## 4. システム構成

```
ブラウザ（React SPA）
   │  HTTPS（同じオリジンの /api/*、Cookie によるセッション）
   ▼
Vercel
   ├─ 静的ファイル（dist/）
   └─ /api/*  → api/router.ts（1つの関数）→ api/_routes/*（機能ごとの処理）
                    │                          ├─ 認証・権限の確認（api/_lib/auth.ts）
                    │                          └─ 入力の検証（shared/schemas.ts）
                    ├─ PostgreSQL（Neon）……Prisma 経由
                    ├─ OpenAI API ……AI による条件の読み取り（任意）
                    ├─ zipcloud ……郵便番号からの住所の自動入力
                    └─ Nominatim（OpenStreetMap）……地名・住所から位置を探す
```

主なフォルダ：

| フォルダ | 内容 |
|---|---|
| `src/` | 画面（React） |
| `api/` | サーバーの処理（Vercel Functions） |
| `shared/` | 画面とサーバーで共通の型・検証ルール・計算（仕入れ案の組み合わせなど） |
| `prisma/` | DB のスキーマ、マイグレーション、初期データ |
| `scripts/` | E2E テスト、デモデータの投入・削除、運営者の付与など |
| `tests/` | 単体テスト |
| `01_spec.md` ほか | 仕様書（`03_spec_addendum.md` は追加の仕様） |

## 5. ローカルでの起動方法

必要なもの：Node.js 22.12 以上、Docker Desktop

```bash
npm install            # 依存パッケージのインストール
npm run env:init       # ローカル用の .env.local を作る（Git には含まれません）
npm run db:up          # ローカルの PostgreSQL（Docker）を起動
npm run db:deploy      # テーブルを作成
npm run db:master      # 品目マスタを登録
npm run db:seed        # テスト用のアカウントと出品（.env.local の DEV_TEST_PASSWORD を使用）
npm run dev            # http://localhost:5173 で起動
```

テスト：

```bash
npm run typecheck      # 型チェック
npm test               # 単体テスト
npm run e2e            # API／E2E テスト（ローカルの開発サーバーと DB に対して実行）
npm run build          # 本番用ビルド
npx tsx scripts/invite-check.ts   # 招待コード方式の確認（ローカルの DB でだけ動く）
```

## 6. 必要な環境変数（名前のみ）

値は `.env.local`（ローカル）と Vercel の環境変数に設定します。**値はリポジトリに含めません。** 見本は `.env.example` にあります。

| 名前 | 用途 | 必須 |
|---|---|---|
| `DATABASE_URL` | PostgreSQL の接続先 | 必須 |
| `DATABASE_URL_UNPOOLED` | マイグレーション用の接続先（Neon） | 本番 |
| `BETTER_AUTH_SECRET` | セッション・リカバリーコードの署名用の秘密の値（32文字以上） | 必須 |
| `BETTER_AUTH_URL` | サービスの URL（独自の URL を使う場合） | 任意 |
| `SIGNUP_MODE` / `SIGNUP_INVITE_CODE` | 新規登録の受け付け方（open／invite／closed）と招待コード | 任意 |
| `OPENAI_API_KEY` / `OPENAI_MODEL` | AI による条件の読み取り（未設定なら手入力のみで動作） | 任意 |
| `AI_DAILY_LIMIT` / `AI_GLOBAL_DAILY_LIMIT` | AI 読み取りの1人あたり／サービス全体の1日の上限 | 任意 |
| `OPERATOR_NAME` / `OPERATOR_EMAIL` / `OPERATOR_PHONE` | 利用規約などに表示する運営者情報 | 任意 |
| `DEV_TEST_PASSWORD` | ローカルのテスト用アカウントのパスワード（本番では使わない） | ローカル |

## 7. デモの使い方

1. https://jimoseri.vercel.app を開き、デモ用のアカウントでログインします。
   - 飲食店：`demo_shop`　／　生産者：`demo_farm`
   - **パスワードはこの README には書いていません。** 発表・提出の資料とは別に、チームから個別にお伝えします。
2. 飲食店でログインすると、自動的に **デモモード（お試し）** になり、架空のデモデータだけが表示されます。
   - 例：受取エリアに「大阪府」、品目に「トマト」を選んで検索 → 地図・一覧に大阪府内のデモの出品が表示されます。
   - 例：仕入れ案で「大阪市福島区・トマト 10kg」→ 3軒の農家を組み合わせた案が表示されます。
3. 仕入れ案や出品の詳細から依頼を送ると、チャットで相談 → 承認 → 取引条件の合意 → 完了確認 → レビュー、の流れを試せます。

新規登録について：発表期間中は、**招待コードが必要な登録方式** にしています（招待コードはチームの関係者にだけ伝えています）。既存の利用者とデモ用アカウントは、そのままログインできます。

デモ用アカウントの制限：

- デモデータ（架空の生産者・出品・受渡拠点）の中だけで動き、実際の利用者・出品・取引には一切届きません。
- パスワード・プロフィールの変更、退会、通報、リカバリーコードの再発行はできません。
- 複数の人が同じアカウントを使うため、チャットに個人情報を書かないでください。
- デモの受渡拠点は、大阪府内の町域の代表地点に置いた架空の拠点です（実在の施設ではありません）。

## 8. セキュリティ上の設計方針

- **秘密情報**：API キー・DB の接続先・認証の秘密の値は環境変数で管理し、リポジトリには含めない（`.env*` は `.gitignore` で除外し、Git の全履歴も検査済み）。OpenAI のキーはサーバー側だけで使う。
- **認証**：パスワードは scrypt でハッシュ化。セッションは HttpOnly・Secure・SameSite=Lax の Cookie。ログイン・登録・リカバリーには回数制限。
- **権限**：すべての API で、サーバー側でログインと役割（飲食店・生産者・運営者）を確認する。他人の出品・取引・チャット・通知は、ID を指定しても「存在しない」として扱う。運営者の役割は利用者自身では付けられない。
- **個人情報の公開範囲**：
  - 住所・電話番号は本人と運営者だけが見る。
  - 電話番号は、本人が「取引相手に表示する」を選んだ場合だけ、取引相手に表示する。
  - 受渡場所の番地・建物名は、マッチングが成立した取引相手にだけ表示する（検索画面では町域まで）。
  - 受渡場所の地図上の位置は、生産者が公開を選んだ場合だけ表示する。
- **Web の一般的な対策**：
  - CSRF：Origin の確認と SameSite Cookie。
  - XSS：React の自動エスケープと Content-Security-Policy。
  - SQL インジェクション：Prisma によるパラメータ化。
  - そのほか：入力は zod で検証し、本文の大きさにも上限を設ける。エラー画面に内部情報を出さない。
- **AI の費用**：1人あたり・サービス全体の1日の上限、出力の長さの上限、タイムアウトを設けている。
- **デモデータ**：実データと区別する目印（isDemo）を持たせ、通常の検索・仕入れ案には混ぜない。
